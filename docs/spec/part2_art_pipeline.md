# Cross Arena 项目规格 · 第二部分：美术管线

LayUDown 独立项目 · 整合版规格（共三部分）· 本部分承接第一部分的命名规范与数据 Schema

> 三部分：第一部分 总纲与规范 · **第二部分 美术管线** · 第三部分 运行时与路线图

---

## 1. 管线总览

```
Blender 模型 / 绑定 / 动作
  → Cel Shading + 描边
  → 固定侧面正交相机，2 倍分辨率渲染 RGBA PNG
  → 缩小 + 裁边 → 原始 PNG 序列（永久保留）
  → 打包 Sprite Sheet + 生成动画元数据
  → 检查报告 → Godot 自动导入
```

三条硬规则：

1. Blender **只负责表现**，不决定伤害和命中（判定见第一部分 FrameData）。
2. **所有动作原地渲染**，不烘焙根位移。移动、跳跃高度、突进位移全部由模拟层按数据控制。
3. 全项目共用一份 `render_spec.json`（相机、像素密度、画布、帧率、描边参数），脚本读取它，不在每个角色里各写一份。

## 2. Blender 角色模板

先做一个通用模板 `character_template.blend`，新角色从它复制。

| 组件 | 要求 |
|---|---|
| 核心骨骼 | Root、Hips、Spine、Neck、Head、双臂、双腿、手指 |
| 辅助骨骼 | 头发、衣物、武器挂载（`Weapon_Mount.R / .L`） |
| 骨骼命名 | 前缀区分用途：`DEF_` 变形、`CTRL_` 控制、`MCH_` 机制；左右用 `.L / .R` |
| 控制器 | 手臂与腿 IK/FK 切换；武器可切换挂载父级（手 / 背 / 腰） |
| 地面参照 | `Ground_Anchor` 空物体，始终投影在角色脚底地面上 |
| 材质 | 基础卡通材质（2 至 3 阶色阶）+ 描边材质 |
| 相机与灯光 | `Render_Cam`（固定侧面正交）+ 固定平行光 |
| 渲染预设 | 读取 `render_spec.json` 自动套用 |

不强制所有角色使用同一套骨骼。最低要求：必须有 `Root` 和 `Ground_Anchor`，并能输出第一部分的核心动作清单。

## 3. 模型要求

- 动漫风格，轮廓清晰，服装层次分明，面数和材质复杂度控制在够用即可。
- 比例通过 `height_scale` 配置管理，不强制统一实际身高，但同一场景中视觉比例要合理。
- 武器与身体绑定关系正确，能支持大幅度攻击动作。

### 侧面可读性检查（建模阶段就做，不要等到渲染）

| 检查项 | 通过标准 |
|---|---|
| 头部侧面比例 | 侧脸轮廓自然，不是正面脸硬转 90 度 |
| 眼睛与面部 | 侧面仍能看出表情与视线方向 |
| 肩膀与手臂遮挡 | 出拳 / 挥剑时手臂不被躯干完全遮住 |
| 武器挥动 | 全程不穿模身体 |
| 头发与服装 | 无明显穿插 |
| 剪影测试 | 把每个关键姿势渲染成纯黑剪影，仍能认出是什么动作 |

## 4. 动画制作

**Action 规则**

- 命名使用第一部分第 7 节的 `Core_ / Combat_ / Skill_ / Presentation_` 前缀，每个动作一个独立 Action，并勾选 Fake User 防止丢失。
- 帧范围以 Action 自身范围为准，渲染脚本自动读取，不手填。
- 头发、衣物等次级运动在渲染前**烘焙缓存**，保证每次重渲结果一致。
- 可选：在 Action 上打 Pose Marker（如 `active_start`），仅作为编写 FrameData 的参考，**不作为判定依据**。

**与战斗时序对齐**

- 动画师按 FrameData 的目标时序制作：命中姿势必须落在有效帧起点对应的那张图上。
- 30 FPS 动画每张图占 2 个模拟帧，因此 FrameData 的前摇和有效帧尽量取偶数；需要奇数帧精度的招式用 60 FPS 渲染。

**质量清单**

- 起手清晰，攻击有力量感，收招自然。
- 重心变化明显，跳跃与落地有重量感。
- 武器轨迹合理，受击有身体反馈。
- 待机不能完全静止，需要呼吸或轻微晃动。
- 不同角色动作风格不同，不得用同一套拳击动作套不同模型。
- 刀光、剑气、弹道等拖尾放进特效层作为独立 Sprite，不烘焙进角色帧。

## 5. 相机与渲染规格

| 项目 | 规格 |
|---|---|
| 相机 | 正交，严格侧面，角色面向画面右侧；不随角色或骨骼运动 |
| 像素密度 | **全角色统一**（每 Blender 单位对应的像素数一致）。身高差异由模型实际尺寸体现，同一战场不会出现大小失衡 |
| 画布 | 每个角色一个固定画布，所有动作共用，不随动作变化 |
| 渲染引擎 | EEVEE，Film Transparent 开启，RGBA 8 位 PNG |
| 色彩管理 | View Transform 用 Standard，避免 Filmic / AgX 破坏色阶 |
| 描边 | 推荐反向外壳法（正交下线宽稳定）；Freestyle 作备选，阿米娅试点时对比后定 |
| 光照 | 固定平行光，从上前方打入，左右翻转后不会显得违和 |
| 抗锯齿 | 2 倍分辨率渲染，再用高质量滤波缩小；缩小时按预乘 alpha 处理，避免白边 |
| 运动模糊 | 关闭 |
| 地面锚点 | `Ground_Anchor` 在每一帧都落在同一个像素位置 |

**画布尺寸先测试再定。** 用一个测试人偶（带最大幅度的武器挥动），在 384、512、768 三种候选最终尺寸下放进 Godot 战斗画面比较清晰度与内存，选定后写入 `render_spec.json`，全项目沿用。

## 6. 朝向处理

- 默认只渲染面向右侧的一套，运行时水平翻转得到左侧（`facing_mode: flip`）。
- 翻转只作用于 Sprite，不改变角色世界坐标和身体碰撞位置；Hitbox 偏移由运行时按朝向镜像。
- 下列情况在动画元数据里标记 `facing_mode: dual`，另渲一套面向左侧的素材：文字或标识、不对称服装、不对称武器、需要固定持握手的武器、翻转后明显出错的动作。
- 左侧版本的渲染方式：**旋转角色 180 度**，相机保持不变。不要镜像模型或相机，否则不对称细节仍然是反的。
- 为统一素材数量而牺牲角色设定是不允许的。

## 7. 输出与 Sprite Sheet

**原始输出**：每个动画一个 PNG 序列目录（`animations/<anim_id>/frame_000.png` 起）。要求 RGBA 透明背景、角色完整不被裁切、帧间无相机漂移、无运动模糊。

**图集规则**

| 项目 | 规则 |
|---|---|
| 划分 | 每个动画独立图集，不做一张总图；帧数很多时拆成多张 |
| 裁边 | 自动裁掉透明边，并把裁切偏移写入元数据，pivot 仍按原画布计算 |
| 间距 | 帧间留 2 像素并向外延展边缘像素，防止缩放时漏色 |
| 尺寸 | 单张不超过 4096×4096（浏览器和旧手机的安全上限） |
| 记录 | 动画名、帧数、帧率、是否循环、每帧区域与偏移 |
| 源素材 | 原始 PNG 序列保留；图集随时可由脚本重新生成，不作为唯一资产 |

**Godot 导入**：导入工具读取元数据，生成运行时资源（图集纹理 + 每帧区域与偏移表）。显示层按模拟层给出的帧号切换图片，**不使用 AnimatedSprite2D 的自动播放**，这样 Hitstop、慢动作和回滚都不会与判定失步。

## 8. AssetPipeline 自动化

**三个独立步骤**，每步可单独运行，失败即停并输出报告：

```
blender -b character.blend --python asset_pipeline/render_character.py -- --character arknights.amiya --anims all
python asset_pipeline/pack_sprites.py --character arknights.amiya
python asset_pipeline/validate.py --character arknights.amiya
```

命令与实现语言可在 Phase 0 调整。要求：支持增量渲染（只重渲 Action 有改动的动画）；每次运行生成检查报告（`metadata/check_report.md`）。

**检查项**

| 检查项 | 级别 |
|---|---|
| Action 缺失或命名不符 | 错误 |
| 帧数为 0，或帧范围与元数据不一致 | 错误 |
| 相机非正交，或参数偏离 `render_spec.json` | 错误 |
| 渲染尺寸不一致 | 错误 |
| 输出文件缺失，或帧号不连续 | 错误 |
| 透明背景异常（画布四角 alpha 不为 0） | 错误 |
| 角色触碰画布边缘（可能被裁切） | 错误 |
| 地面接触点偏移超过 1 像素 | 错误 |
| 核心动作缺失且未声明 `unsupported` | 错误 |
| 缺少 `sources.json` 或未覆盖全部素材 | 错误 |
| 非跳跃动画中脚底位置跳动 | 警告 |
| 相邻帧差异异常大（可能穿帧或突变） | 警告 |
| 图集超出尺寸上限 | 警告 |

## 9. 内存预算（初始目标，需实测修正）

| 项目 | 估算与目标 |
|---|---|
| 单帧 512×512 RGBA | 未压缩约 1 MiB；裁边后平均约 0.4 至 0.6 MiB |
| 单角色常驻目标 | 不超过 64 MiB（约 120 帧等效） |
| 战斗场景总目标 | 两名角色 + 特效 + 场景不超过 160 MiB |

**降低手段**：裁边；默认 30 FPS；循环动画尽量少帧；相同的帧共用一张图；登场、胜利等低频动画延迟加载。

**加载策略**：角色选择界面只加载头像和立绘；进入战斗才加载选定的两名角色；退出战斗立即释放。

**压缩**：带描边的透明图使用显存压缩容易出现杂边，默认不压缩，只有在目标设备上测试通过后才启用。

手机和浏览器是最紧的平台。以上数值在 Phase 0 和阿米娅试点时，用目标设备实测后修正。

## 10. 本部分验收标准

- Blender 能稳定、可重复地导出角色动画。
- 自动化工具能批量渲染并生成元数据与图集，不需要人工逐帧导入。
- 所有角色使用同一份 `render_spec.json`，视觉规格一致（像素密度、光照、描边、地面锚点）。
- 检查报告能发现第 8 节列出的全部错误类型。
- 阿米娅试点的具体动作清单与 Godot 端验证项，见第三部分第 14 节。
