# 运行时

## 1. 架构总图

```
┌─────────────────────────────────────────────────────┐
│ 表现层（Godot 节点）                                │
│ FighterView · Stage · Effects · HUD · 菜单          │
│ 只读取模拟状态，不写回                              │
├─────────────────────────────────────────────────────┤
│ 适配层                                              │
│ 输入采集（键盘 / 手柄 / 触屏 / AI / 网络）          │
│   → 每帧输入位掩码                                  │
│ 事件队列（音效 / 特效，带帧号）                     │
├─────────────────────────────────────────────────────┤
│ 模拟层（纯数据，确定性，固定 60Hz）                 │
│ Core · Combat · Fighter · HitSystem                 │
│ SkillSystem · ComboSystem                           │
├─────────────────────────────────────────────────────┤
│ 数据层                                              │
│ DataLoader：读取 ip_content/*，JSON → 运行时资源    │
├─────────────────────────────────────────────────────┤
│ 内容包 ip_content/<ip>/...                          │
└─────────────────────────────────────────────────────┘
上层只读取下层；模拟层不依赖任何 Godot 节点，也不认识任何具体 IP。
```

## 2. 确定性模拟核心

**核心接口**：`step(state, inputs) -> state`。给定相同的初始状态和相同的每帧输入，结果必须逐位相同。

**必须遵守**

- 固定 60Hz 步进。Godot 端用累加器驱动，渲染帧率不影响模拟步数。
- 位置、速度、伤害等全部用整数（1 像素 = 1000 单位）；除法用整数除并固定取整方式。
- 随机数只用带种子的自研 RNG，种子和当前状态存在模拟状态里。
- 不读取墙钟时间，不依赖字典遍历顺序（用有序数组），不持有节点引用。
- 模拟状态是一个纯数据结构，包含：双方角色状态、投射物列表、回合 / 计时状态、输入缓冲、命中登记表、RNG 状态、帧号。

**快照、恢复、重放**

- `save_state()` 与 `load_state()` 必须开销小（状态体积小、无深层引用），这是回滚联机和训练模式重置的基础。
- 输入以「每帧每玩家一个位掩码」记录，整局输入序列即为录像。
- 每帧可计算状态校验和（checksum），用于重放测试与未来联机对账。

**更新顺序（每个模拟帧）**

1. 读取双方输入，更新输入缓冲。
2. 更新角色状态（状态机、取消判断、技能触发）。
3. 应用速度与重力，移动，处理场地边界与身体挤压。
4. 更新投射物。
5. 命中检测与结算（第 5 节）。
6. 处理 Hitstop 计数、硬直递减、能量与计时。
7. 判断回合胜负。
8. 输出事件队列（音效、特效、震屏请求，仅表现用）。

## 3. 战场与镜头

- 严格 Side View：X 轴左右移动，Y 轴跳跃与落地，**不存在 Z 轴移动**，不使用 Y-Sort 决定角色前后关系。
- 两名角色自动面向对手；攻击过程中朝向锁定；必杀技期间按配置处理朝向。
- 场地有左右边界；角色之间有身体碰撞盒（pushbox），互相挤压时按整数规则推开；角落受击时的反推规则写成数据。
- **镜头只属于表现层**，不进入模拟状态。镜头跟随、缩放、震屏、闪白都不得影响判定。
- 渲染分层（Z Index）：Background → BackgroundDecoration → Battlefield → Fighter → GroundEffect → ForegroundEffect → UI。

## 4. 角色状态机

状态：`IDLE`、`WALK_FORWARD`、`WALK_BACKWARD`、`DASH`、`CROUCH`、`JUMP`、`ATTACKING`、`BLOCKING`、`HITSTUN`、`BLOCKSTUN`、`KNOCKDOWN`、`WAKEUP`、`THROWING`、`SKILL`、`ULTIMATE`、`DEAD`。

回合流程（INTRO、FIGHT、KO、ROUND_END、MATCH_END）属于 Combat 模块，不混进角色状态机。

**转换规则（转换表写成数据，不散落在代码判断里）**

| 当前状态 | 可转入 |
|---|---|
| IDLE / WALK / CROUCH | 任何地面动作：攻击、技能、跳跃、冲刺、防御、投技 |
| DASH | IDLE；按角色配置可取消进入攻击 |
| JUMP | 空中攻击、空中技能；落地 → IDLE |
| ATTACKING / SKILL / ULTIMATE | 动作结束 → IDLE / CROUCH / JUMP；取消窗口内 → 其他攻击、技能、必杀技 |
| BLOCKING | 松开防御且无防御硬直 → IDLE |
| HITSTUN | 硬直结束 → IDLE；空中受击落地 → KNOCKDOWN |
| BLOCKSTUN | 结束 → BLOCKING（仍按住防御）或 IDLE |
| KNOCKDOWN | 动画结束 → WAKEUP → IDLE（起身可配置无敌帧） |
| THROWING | 结束 → IDLE（被投者在 HITSTUN 中播放绑定的投技动画） |
| DEAD | 终态 |

**优先级规则**：受击（HITSTUN / BLOCKSTUN）高于一切主动状态，除非处于无敌或霸体帧。每个状态记录自己的帧计数，进入快照。

## 5. 判定系统

**数据来源**

- 攻击框：来自 FrameData 的 `hitboxes`，按「招式 ID + 当前招式帧」取出。
- 受击框：来自角色目录 `framedata/hurtboxes.json` 的配置（即 `character.json` 里的 `hurtboxes` 所指的配置名），按状态区分站立 / 下蹲 / 空中 / 倒地。FrameData 可选 `hurtbox_override` 字段按帧覆盖（例如手臂伸出时扩大受击框）。这是对第一部分 Schema 的补充。
- 全部为整数矩形，检测用整数 AABB 相交。镜像按 `facing_direction` 在运行时计算。

**命中结算流程**

1. 遍历攻击方当前有效的攻击框，对防守方每个受击框做相交检测。
2. 防守方处于无敌帧则忽略；处于霸体帧则吃伤害但不进入硬直。
3. 查**命中登记表**：同一招式实例的同一攻击框对同一目标只命中一次。多段攻击用不同 `hit_index` 区分，各段各自登记。
4. 双方同帧互相命中：比较 `priority`；相同则判为互打（Trade），双方都受击。
5. 判断防御：防御方处于 BLOCKING 且防御方向有效 → 进入 BLOCKSTUN，扣少量或零伤害；否则 → HITSTUN。
6. 写入伤害、击退、硬直、Hitstop，更新连招计数与能量，向事件队列推送命中事件。

**投射物**：模拟层的独立实体，有自己的矩形、速度、生命周期和命中数据（由 SkillDefinition 与 FrameData 的 `projectile_spawn` 定义），与角色用同一套命中结算。

**投技**：近距离矩形检测，不可被防御，被投者处于无敌或空中时失败。

**调试模式**：叠加绘制攻击框（红）、受击框（蓝）、身体框（绿）、当前状态与帧数。训练模式默认开启。

## 6. 输入与缓冲

- 每帧每玩家输入为一个位掩码：方向（上下左右）+ 按键（轻、中、重、技能、防御、冲刺等）。键盘、手柄、触屏、AI、网络最终都转成同一种位掩码。
- **输入缓冲**：按键保留约 6 帧，状态允许时自动触发，避免快速输入丢指令。缓冲帧数做成全局配置。
- **指令识别**：方向序列（如下前 + 按键）在约 15 帧窗口内识别，允许轻微宽容。指令定义写在 SkillDefinition 的 `input` 字段里，不写进代码。
- 左右同时按下视为中立。
- 触屏方案：虚拟摇杆 + 大按键，指令技能提供一键快捷入口，使用同一位掩码，不改变模拟规则。

## 7. 连招、技能与能量

**取消与连招**

- 取消窗口来自 FrameData 的 `cancel_windows`。默认链：轻 → 中 → 重 → 技能 → 必杀技；角色可在数据中增减。
- 空中连招：受击者在空中的浮空次数与浮空高度设上限，达到上限后不再被追击。
- 连招计数：同一连招内的命中数；受击者恢复行动后清零。
- **伤害递减**（整数百分比表，初始建议）：第 1 段 100%，之后依次 90、80、70、60、50、40，最低保持 30。
- **防无限连**：硬直随连招段数递减；浮空次数上限；同一招式在一次连招中使用次数上限。

**技能**

- 技能类型见第一部分枚举。伤害、判定、击退来自对应的 FrameData；冷却（帧数）、消耗、输入方式来自 SkillDefinition。
- 技能不得假设「只是播放一段特效图片」：每个技能都必须有对应的判定、状态变化和表现事件。

**能量**

- 能量条随命中、被击、防御增长，数值写在 FighterDefinition 或技能配置中。
- 必杀技消耗整条或部分能量；技能取消必杀技额外消耗。训练模式可设无限能量。

## 8. 命中停顿与战斗表现

**属于模拟层的**（会影响后续帧结果，必须确定性）：

- **Hitstop**：命中后双方冻结若干模拟帧（轻 6、中 8、重 10，初始建议；数值写在 FrameData 命中数据里）。冻结期间状态计数、动画帧计数、投射物都暂停，恢复后从原帧继续。
- **必杀技暂停（Super Freeze）**：必杀技发动时的定格帧数，作为模拟暂停处理，长度固定。

**属于表现层的**（只读状态，不影响判定）：

- 命中闪光、打击火花、屏幕震动、屏幕闪白、背景暂停、局部镜头放大。
- 伤害数字、连招计数显示。
- 必杀技镜头与全屏特效。

规则：表现层的特效由模拟层输出的**事件队列**触发（事件带模拟帧号）。回滚重演时用帧号去重，避免特效和音效重复播放。

## 9. Godot 渲染层

**角色显示节点（只显示，不做物理和判定）**

```
FighterView (Node2D)
  Shadow (Sprite2D)
  CharacterSprite (Sprite2D)    # 每个模拟帧由状态指定图集区域
  Effects (Node2D)
  DebugDraw (Node2D)            # 调试框叠加
```

模拟状态是纯数据，不是节点；`FighterView` 每帧读取状态后更新自己。所有角色复用同一个 `FighterView` 场景和脚本，个性只来自数据与图集。

**帧映射算法（整数运算）**

- 每个角色状态维护 `anim_tick`：在当前动画内已经过的模拟帧数，Hitstop 期间不增加。
- 显示帧序号 = `(anim_tick * animation_fps) / 60`（整数除法，向下取整）。
- 循环动画对 `frame_count` 取模；非循环动画停在最后一帧。
- 30 FPS 动画每张图显示 2 个模拟帧，60 FPS 动画一对一，其他帧率同理。
- 动画中断时 `anim_tick` 归零；需要从指定帧恢复时直接设置 `anim_tick`。

**朝向与坐标**

- 水平翻转只作用于 `CharacterSprite`，不影响世界坐标和判定。Hitbox 偏移按 `facing_direction` 镜像，不靠 Sprite 的翻转。
- 显示位置 = 模拟位置 ÷ 1000，再加上图集裁边偏移与 pivot 偏移，保证脚底不抖动。

**平滑显示（可选）**：显示器刷新率高于 60Hz 时，可对位置做视觉插值，但不得写回模拟状态。

## 10. 游戏模式

三种模式共用同一个模拟核心，只是输入来源和规则开关不同。

**人机对战**

- AI 与玩家用同样的输入位掩码接口，每帧输出输入；**只能读取当前模拟状态与过去的输入，不能读取玩家未来输入**。
- 难度通过行为策略区分，而不是只改伤害：反应延迟、进攻倾向、防御概率、连招执行能力、失误率、技能使用时机。
- AI 参数来自 FighterDefinition 的 `ai_profile` 与难度配置，不写进核心代码。

**训练模式**

- 无限生命、无限能量；显示攻击框与受击框；显示角色帧数据（前摇 / 有效 / 收招、优势帧）与连招信息。
- 一键重置双方位置（利用状态快照）。
- 训练假人行为：站立、下蹲、跳跃、全防御、首次命中后防御、录制 / 回放、CPU。

**在线对战（预留）**

- 流程：创建房间 → 加入房间 → 准备 → 选角 → 战斗 → 结算 → 再来一局。
- 首期只定义接口和流程，不实现。

## 11. 战斗 UI 与多平台

**战斗画面元素**：左侧己方头像、右侧对手头像、双方血条、能量条、倒计时、连招计数、角色名、必杀技提示、回合结果。

**风格要求**

- 有辨识度，有动漫格斗游戏的氛围，**角色视觉占据主要画面**。
- 不堆砌圆角卡片，不使用模板式 AI 界面，不使用无意义的渐变和装饰。
- 动画效果服务于战斗反馈。
- 选角界面以角色立绘和选中效果为主，不使用数据库管理页面风格。

**多 IP 界面**：主界面 → IP 选择（封面、名称、代表角色、可用角色数、简介、是否开放）→ 角色选择（网格、头像、预览、详情、技能简介）。未开放的 IP 显示为未开放，不提供假入口。

**平台适配**：桌面与手机共用同一套 UI 数据；手机端有触控按键布局与安全区适配，横屏优先。UI 只读取模拟状态，不写回。

## 12. 联机预留

首期不实现联机，但以下约束从第一天起就必须满足，否则后期无法补：

- 模拟确定性（第 2 节全部条款）；同一份输入重放，每帧校验和必须一致。
- 状态可快照、可恢复，开销足够小以便每帧保存。
- 输入与模拟分离；网络只同步输入，不同步角色坐标。
- 事件队列带帧号，回滚后可去重。
- 表现层可从任意模拟状态重新生成，不保存独立的表现状态。

**后期工作（Phase 6）**：输入预测与回滚、延迟测试、断线处理；评估现有的 Godot 回滚方案（Phase 0 调研时一并研究）；浏览器端的传输方案；联机服务独立部署，端口在检查已占用端口后另选，不得影响 18815。

# 路线图

## 13. 分阶段计划

必须分阶段推进，每个阶段通过验收后才进入下一阶段。

| 阶段 | 目标 | 主要交付 | 验收标准 |
|---|---|---|---|
| **Phase 0** 调研与规划 | 只读检查与规划，不修改现有项目 | 环境检查报告、本规格三部分、风险与资源清单 | 你审核通过 |
| **Phase 1** 最小可玩原型 | 最小战斗闭环 | 确定性模拟核心、两个测试角色（占位素材，放在独立的测试内容包并在 `sources.json` 标明占位）、移动、跳跃、普攻、防御、受击、生命值、胜负 | 两个角色能完成一场完整基础对局；同一输入录像重放校验和一致 |
| **Phase 2** 战斗系统完善 | 完整战斗规则 | 完整状态机、连招与取消、技能、必杀技、帧数据、Hitbox / Hurtbox、特效、训练模式、AI | 能进行有攻防、连招、技能差异的完整战斗；训练模式能显示判定与帧数据 |
| **Phase 3** Blender 角色生产线 | 生产线验证 | 角色模板、骨骼规范、动画模板、Cel Shading、批量渲染、图集导入、元数据、检查报告 | 一个正式角色（阿米娅）完整走通全流程，Godot 端验证项全部通过（第 14 节） |
| **Phase 4** 明日方舟 IP | 首个 IP 上线 | IP 入口、选角界面、至少两个完整可玩角色、技能差异、角色动画、特效、专属场景 | 两个角色各自通过完整对局验证；其余候选角色按资源逐步加入 |
| **Phase 5** 多 IP 扩展 | 验证架构 | 第二个 IP 的内容包 | 只新增内容包即可接入，核心战斗代码零修改 |
| **Phase 6** 联机与部署 | 在线对战 | 房间系统、回滚同步、延迟处理、断线恢复、部署方案 | 联机对局通过延迟测试；整合现有网站前先评估并经你确认 |

**通用门禁**：每个阶段结束都要在目标平台（Windows、浏览器）实际运行并完成真实对局，再进入下一阶段；动画、判定、技能都必须经过实机对局验证。

## 14. 阿米娅试点

第一位正式制作的角色。先做以下动作：

- 待机、前进、后退、跳跃
- 轻攻击、重攻击
- 受击、防御
- 一个远程技能
- 一个必杀技

**导入 Godot 后的验证项（全部通过才算试点成功）**

1. Sprite 帧序列是否正确。
2. 动作是否连续。
3. 角色是否始终保持正确比例。
4. 脚底是否出现跳动。
5. 左右翻转是否正常。
6. 武器是否出现穿插或错误翻转。
7. 动画与攻击判定是否同步。
8. Hitstop 是否正确。
9. 动画能否正确中断和恢复。
10. 浏览器与 Windows 导出是否正常。

阿米娅通过完整战斗测试后，再制作陈。生产线未经验证时，不批量制作角色。

**提醒**：阿米娅是受版权保护的角色。模型与动作必须自制或有明确授权，并在 `sources.json` 登记；公开发布前先评估授权。

## 16. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 模拟不确定（浮点、随机、遍历顺序） | 回放不一致，联机无法回滚 | 纯整数模拟；校验和重放测试从 Phase 1 起常驻 |
| 美术产量不足 | 角色数量上不去 | 先做一个角色验证生产线；核心动作先行，专属动作后补；自动化减少人工 |
| 侧面视角模型变形 | 返工成本高 | 建模阶段就做侧面可读性检查与剪影测试 |
| 内存与包体（手机、浏览器） | 卡顿、崩溃、加载慢 | 裁边、帧率控制、按需加载；用目标设备实测预算 |
| Web 导出限制 | 浏览器版无法按预期运行 | Phase 0 用空项目试导出，确认响应头与托管要求 |
| EEVEE 后台渲染环境 | 无法在服务器批量渲染 | Phase 0 验证；备用方案：本机渲染或改用其他渲染引擎 |
| 版权与授权 | 无法公开发布 | 素材来源登记；公开或商业化前评估授权；先作为个人学习项目 |
| 手感调优耗时 | 进度拖延 | 帧数据外置于 JSON；训练模式显示数据；小步调整，每次实机验证 |
| 联机复杂度 | 后期无法补做 | 第 12 节约束从第一天遵守，联机本身推迟到 Phase 6 |
| 手机端格斗操作 | 体验差 | 触屏布局早期就做原型并实测；提供一键技能入口 |
| 范围蔓延 | 项目失控 | 阶段门禁；不通过验收不进入下一阶段 |
| 影响现有服务 | 生产故障 | 严守安全红线；独立仓库与测试环境；任何涉及现有服务的操作先确认 |
